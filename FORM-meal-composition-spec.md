# Спецификация: форма «Приём пищи и состав блюда» — редизайн + backend

**Проект:** meal-provisioning-ai · **Статус репо:** main `1268583e` (Known Bug #1 и N+1 в SummaryService уже закрыты PR #44–46) · **Вход:** макет модалки «Добавить приём пищи» со встроенным редактором состава
**Связь с эпиком:** уточняет задания T3 (схема), T4 (эндпоинты), T5 (расчёты), T8 (UI). Документ — вход для агента.

---

## 1. Диагноз макета: почему «наляпано»

| # | Проблема | Почему болит |
|---|---|---|
| 1 | **Два коммита в одном окне**: «Сохранить состав» и «Добавить в приём пищи» | Неопределённая матрица состояний: можно сохранить состав не добавляя приём? Добавится ли несохранённый состав? Куда вообще пишутся правки — в справочник блюда или в поход? Кнопки конкурируют за главное действие |
| 2 | **Смешаны два интента**: «добавить приём» (быстрое решение: блюдо+день+люди) и «отредактировать состав» (медленная детальная работа) | Редактор состава показан ДО существования приёма — правки висят в воздухе; модалка вырастает в простыню; пользователь, которому нужно просто добавить ужин, видит таблицу правок |
| 3 | **Три механики правки без семантики**: корзина на строке, «Заменить», строка добавления | Корзина = исключить из приёма? удалить из справочника? необратимо? «Заменить» открывает что? Ни статусов строк, ни объяснений, ни обратимости |
| 4 | **Количества без базы**: «0,03 шт», «0,35 л», «1 шт» | Непонятно: на порцию? на приём? на 4 человек? Поле «Количество человек» стоит НИЖЕ и визуально не связано — меняет ли оно цифры выше? |
| 5 | **Единицы не бьются с каталогом**: картофель сублимированный в «шт» | В каталоге он KG; нет подсказок фасовки («≈ 1 упаковка 50 г»), нет веса штуки — пользователь не может свериться с реальностью |
| 6 | **Нет контекста дня/даты в шапке** | Модалка оторвана от карточки дня, из которой открыта; на яхте/в походе с 7 днями легко положить ужин не в тот день |
| 7 | **Нет превью блюда до добавления** | 201 блюдо в списке; пользователь выбирает вслепую — без ккал, времени готовки, категории, хотя всё это есть в данных |
| 8 | **«Сохранить состав» звучит как правка справочника** | Опасная двусмысленность: админ ожидает правку рецепта глобально, юзер — только своего приёма. Ни один сценарий не проговорён |
| 9 | **Нет dirty-state**: «Отмена» молча теряет правки; нет «Сбросить изменения» | Правки состава — самая трудоёмкая операция формы, терять её обидно |
| 10 | **Строка добавления продукта равновесна строкам состава** | Поиск+«Кол-во»-кнопка создают визуальный шум внутри таблицы; подсказка мелким текстом компенсирует плохую аффордансность вместо того чтобы её чинить |

**Вывод:** форма пытается быть четырьмя инструментами сразу (добавление приёма, редактор состава, замены, people-override). Лечится разделением: **два окна, одно решение в каждом**, и серверным контрактом, где каждая кнопка имеет ровно одну семантику.

## 2. Целевая модель: Модалка A + Модалка B

### 2.1. Модалка A — «Добавить приём пищи» (быстрая)

```
┌──────────────────────────────────────────────────────┐
│ Добавить приём пищи                              [×] │
│ ▸ День 3 · сб, 12 октября · «Осенний Кавказ»          │  ← контекст из карточки дня
│                                                      │
│ Тип приёма                                           │
│ [Завтрак] [Обед] [Ужин●] [Перекус]                    │  ← segmented, дефолт = тип кнопки
│                                                      │
│ Блюдо                                                │
│ [🔎 Уха из рыбных консервов                 ⌄]       │  ← комбобокс с поиском
│ ┌──────────────────────────────────────────────────┐ │
│ │ Уха из рыбных консервов      СУПЫ · готовка 25 мин│ │  ← превью-карточка
│ │ 185 ккал/порция · сайра, картофель, морковь, лук   │ │     (топ-4 состава + ккал из T2)
│ └──────────────────────────────────────────────────┘ │
│                                                      │
│ Количество человек      [ −  4  + ]   по умолчанию 4  │  ← степпер
│                                                      │
│                  [Отмена]        [Добавить]           │  ← ОДНА commit-кнопка
│            [ ] добавить и настроить состав            │  ← чекбокс-шорткат → после
└──────────────────────────────────────────────────────┘     добавления открыть B
```

Поведение:
- Контекст дня/даты/похода — всегда в шапке (проп из карточки дня).
- Segmented-контрол на 4 типа вместо select: быстрее, все варианты видны.
- При выборе блюда — превью-карточка: категория, cook_minutes, **ккал/порция** (поле из T2), чипы топ-4 ингредиентов. Ккал пересчитывается при смене людей? Нет: ккал/порция не зависит от людей; рядом мелко «на 4 чел: 740 ккал».
- Люди: степпер 1–20, пусто = «по умолчанию N» (trip.defaultPeople); плейсхолдер показывает N.
- Ровно одна commit-кнопка «Добавить» → `POST /trips/{t}/days/{d}/meals`. Состав НЕ редактируется здесь.
- Шорткат «добавить и настроить состав»: после успешного POST открывается Модалка B для созданного приёма (или action в тосте «Приём добавлен · Настроить состав»). Выбор агента: чекбокс проще для теста.
- Ошибки: 409/400 — ProblemDetailAlert; блюдо не выбрано — кнопка disabled.

### 2.2. Модалка B — «Состав приёма» (только для существующего приёма)

Открывается: с карточки приёма (кнопка-иконка «Состав»), шорткатом из A, и из меню-строки. Редактирует **только этот приём**; справочник блюда не трогает (админ правит глобально в RecipesPage, T7).

```
┌───────────────────────────────────────────────────────────────┐
│ Состав приёма · День 3 · 12 октября · Ужин                [×] │
│ Уха из рыбных консервов · 4 человека                          │
│ ⓘ Правки применяются только к этому приёму — блюдо в          │
│   справочнике не изменяется                                   │
│                                                               │
│ ПРОДУКТ                  КОЛ-ВО НА ПРИЁМ   СТАТУС      ДЕЙСТВИЯ│
│ Рыбные консервы 250 г      [1    ] шт      из рецепта  [Зам][Иск]│
│ Вода питьевая              [1,4  ] л       из рецепта  [Зам][Иск]│
│ Картофель сублимированный  [0,18 ] кг      ×1,5 изм.   [Сбр][Иск]│
│ Лавровый лист              [ ——— ]         исключён    [Верн]   │
│ Лимон                      [0,25 ] шт      добавлено   [Удал]   │
│                                                              ⚑ф│
│ ─────────────────────────────────────────────────────────────│
│ [🔎 Найти продукт в справочнике…          ] [кол-во] [+ Добавить]│
│                                                               │
│ Итого на приём: 740 ккал · 1,62 кг · план 412 ₽               │
│ Изменения не сохранены ●            [Сбросить]  [Сохранить]    │
└───────────────────────────────────────────────────────────────┘
```

Правила строк:
- **Количество показано НА ПРИЁМ** (= per-serving × people, scale 3), единица из каталога; под инпутом мелко фасовка: «≈ 2 упак × 50 г» (pack_size) или «1 шт = 250 г» (piece_weight_g). Редактирование числа рецептурной строки → состояние `×N изм.` (SCALE).
- **Статусы-бейджи** (ровно 5): `из рецепта` · `×N изм.` · `добавлено` (+подпись «фикс. кол-во») · `исключён` (строка приглушена, quantity задизейблен, зачёркнут) · `заменён → {имя}` (у строки-получателя замены).
- **Действия по состоянию** (никаких универсальных корзин):
  - из рецепта / ×N: `[Заменить]` `[Искл.]` ; у `×N` дополнительно `[Сброс]` (вернуть ratio=1)
  - добавлено: `[Удал]` (только EXTRA можно удалять) + `[Искл.]` не нужен (удаление покрывает)
  - исключён: `[Вернуть]`
  - заменён: бейдж + `[Отменить замену]`
- **Добавление продукта**: поиск по имени; количество обязательно (>0); если продукт УЖЕ в составе и не исключён — инлайн-подтверждение «уже в составе (0,12 кг) — установить 0,18?» (превращается в SCALE, новой строки нет); если исключён — «вернуть и установить количество?».
- **Замена** (`[Зам]`): инлайн-раскрытие строки: поиск продукта-цели + ratio (авто 1,0; для разных единиц предупреждение «единицы различаются: кг → шт» и обязательный ручной ratio). Создаёт substitution (trip-level, как есть в схеме).
- **Люди**: меняются НЕ здесь (карточка приёма / модалка A до создания). При изменении people вне B: рецептурные и SCALE-строки перемасштабируются автоматически, EXTRA — нет; B показывает баннер--note: «добавленные позиции — фиксированное количество на приём, при смене людей не меняются».
- **Dirty-state**: точка в заголовке, «Сохранить» disabled когда чисто, «Сбросить» возвращает к серверному состоянию, закрытие с правками — confirm.
- **Итоги внизу**: ккал на приём, вес (г/кг), план-стоимость на приём (цены дня) — пересчитываются live из эффективных количеств (клиент может считать превью локально из kcalPer100g/цен в ответе composition; authoritative-пересчёт всех экранов — после Сохранить через summary).
- Одна commit-кнопка «Сохранить» → **batch `PUT /trips/{t}/meals/{m}/composition`** (атомарно), затем refetch summary (T6-пайплайн) — все вкладки согласуются.

### 2.3. Что удалено из макета
- Кнопка «Сохранить состав» из окна добавления (коммит один на окно).
- Редактор состава из окна добавления (переехал в B).
- Универсальные корзины на строках рецепта (исключение — обратимый toggle; удаление — только EXTRA).
- Отдельная кнопка-инпут «Кол-во» в строке добавления (количество — поле рядом с поиском, обязательное).

## 3. Семантика количеств и состояний (контрактная правда)

| Сущность | Хранение | Масштабирование людьми | UI-статус |
|---|---|---|---|
| Рецептурная строка | `recipe_ingredients.amount` на `base_servings` | да (derived = amount/baseServings × people) | `из рецепта` |
| Изменённое количество | adjustment `kind=SCALE`, `ratio` | да (derived × ratio) | `×N изм.` |
| Добавленный продукт | adjustment `kind=EXTRA`, `amount` — **абсолют на приём** | **нет** (фикс.) | `добавлено` |
| Исключённый | adjustment `kind=EXCLUDE` | — | `исключён` |
| Замена | `trip_ingredient_substitutions` (trip, recipe, from→to, ratio) | применяется к итоговому количеству | `заменён → X` |

Порядок применения в расчёте (фикс, в ARCHITECTURE.md):
```
qty(ing, meal) = Σ_receptRow( base/baseServings × people × ratio_SCALE )   [EXCLUDE пропускаются]
               + Σ_EXTRA( amount )                                          [абсолют, без people]
затем substitutions: qty[to] += qty[from] × ratio_sub;  qty[from] := 0
   (adjustments исходного from-ингредиента переносятся на to вместе с количеством)
```
Округления — эталон эпика §3.4: количества scale 3 HALF_UP; показ humanize; деньги scale 2.

## 4. Backend: что добавить

### 4.1. Миграция V19 (уточнение схемы из эпика T3)
```sql
CREATE TABLE trip_meal_adjustments (
    id BIGSERIAL PRIMARY KEY,
    trip_id BIGINT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
    meal_id BIGINT NOT NULL REFERENCES trip_meals(id) ON DELETE CASCADE,
    ingredient_id BIGINT NOT NULL REFERENCES ingredients(id) ON DELETE CASCADE,
    kind VARCHAR(10) NOT NULL CHECK (kind IN ('EXCLUDE','EXTRA','SCALE')),
    amount NUMERIC(10,3) CHECK (amount > 0),        -- только EXTRA
    ratio  NUMERIC(8,4)  CHECK (ratio > 0),         -- только SCALE
    comment VARCHAR(500),
    created_by BIGINT REFERENCES users(id),
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    UNIQUE (meal_id, ingredient_id),
    CHECK ( (kind='EXTRA' AND amount IS NOT NULL AND ratio IS NULL)
         OR (kind='SCALE' AND ratio  IS NOT NULL AND amount IS NULL)
         OR (kind='EXCLUDE' AND amount IS NULL AND ratio IS NULL) )
);
CREATE INDEX idx_tma_trip ON trip_meal_adjustments(trip_id);
-- + trip_manual_items, trip_shopping_exclusions — без изменений из эпика T3
```

### 4.2. Эндпоинты состава (уточнение T4)
```
GET /trips/{t}/meals/{m}/composition
→ {
    mealId, dayDate, mealType, people, baseServings, recipeId, recipeName,
    items: [{
      ingredientId, name, unit, packSize, pieceWeightG, kcalPer100g,
      baseAmountPerServing,      // из рецепта (null для EXTRA)
      derivedAmount,             // base/baseServings×people (null для EXTRA/EXCLUDED)
      effectiveAmount,           // итог с учётом SCALE/EXCLUDE(0)/EXTRA
      state: RECIPE|SCALED|EXTRA|EXCLUDED,
      ratio?, substitutedFrom?,  // state=SCALED / строка-получатель замены
      kcalTotal                  // kcalPer100g × effectiveAmount
    }],
    substitutions: [{ id, fromIngredientId, fromName, toIngredientId, toName, ratio }],
    totals: { kcal, weightGrams, plannedCost }     // plannedCost по цене дня приёма
  }
— сервер считает ВСЁ масштабирование; клиент не делит и не умножает.

PUT /trips/{t}/meals/{m}/composition          (атомарный диф-коммит модалки B)
body: {
  items: [{ ingredientId, state: RECIPE|SCALED|EXTRA|EXCLUDED, amount?, ratio? }],
  substitutions: [{ fromIngredientId, toIngredientId, ratio }]
}
→ сервер диффит с текущим состоянием, создаёт/удаляет adjustments и substitutions
  в ОДНОЙ транзакции; ответ = новый GET composition.
Валидации: amount/ratio > 0; state=EXTRA→amount, SCALED→ratio; ingredient существует;
  meal принадлежит trip; trip принадлежит юзеру (иначе 404); дубли ingredientId → 400.
```
Гранулярные `POST/DELETE adjustments` из T4 остаются (e2e, API-полнота), но UI-форма ходит только в batch PUT — один round-trip, нет частичных состояний.

### 4.3. Расчёт (уточнение T5)
- `computeShopping`/menu (после PR #44–46 — общий конвейер) применяет порядок из §3: EXCLUDE → SCALE → people → EXTRA → substitutions с переносом adjustments.
- `substitutedFrom` заполняется именем from-ингредиента; строка from не показывается (qty=0).
- kcal/weight/plannedCost в totals composition и в summary/kpi — один калькулятор (T2).

### 4.4. Mock-паритет и тесты (обязательно, культура репо)
- mockServer: роуты composition GET/PUT с той же семантикой (in-memory adjustments).
- Contract-тесты (mock==real): (1) SCALE ×1.5 меняет qty в shopping и ккал в menu; (2) EXTRA не масштабируется при смене peopleOverride; (3) EXCLUDE убирает строку из закупок и ккал, но composition возвращает её с state=EXCLUDED; (4) замена переносит количество и SCALE-корректировку на to; (5) batch PUT идемпотентен при повторе того же тела.
- Unit (backend): масштабирование base/baseServings×people×ratio (scale 3), вес/ккал строки, plannedCost по цене дня приёма.
- Component (frontend, coverage ≥80%): Модалка A (превью, disabled-кнопка, шорткат), Модалка B (dirty-state, бейджи, merge-подтверждение при добавлении существующего, confirm при закрытии с правками).

## 6. Чек-лист приёмки формы

- [ ] В окне добавления — одна commit-кнопка; состав не редактируется; есть контекст дня и превью блюда (ккал/время/состав).
- [ ] «Добавить и настроить состав» открывает B для созданного приёма.
- [ ] В B: количества на приём с фасовочными подсказками; 5 статусов-бейджей; действия соответствуют статусу (исключить/вернуть, сброс ratio, удалить только EXTRA, отменить замену).
- [ ] Добавление уже имеющегося продукта предлагает изменить количество строки, а не создаёт дубль.
- [ ] Смена людей (вне B) перемасштабирует рецептурные и SCALE-строки и НЕ трогает EXTRA; в B виден баннер-пояснение.
- [ ] «Сохранить» — один batch PUT; после него закупки/на человека/чеки/KPI пересчитаны (факт-цены учитываются).
- [ ] Dirty-state: точка, disabled-«Сохранить» когда чисто, «Сбросить», confirm при закрытии.
- [ ] Справочник блюда правками из B не изменяется (подпись в шапке B); админ-правка справочника — из RecipesPage.
- [ ] Contract mock==real зелёный; component-тесты модалок ≥80% lines; e2e-mock: исключил ингредиент → закупка уменьшилась.
