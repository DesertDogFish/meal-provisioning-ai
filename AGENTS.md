# AGENTS.md

Правила для AI-агентов, работающих в репозитории. Статус задач и планы — в папке `plans/`, формулы и контракты — в `ARCHITECTURE.md`, дизайн — в `provisions/design-pack/` и `DESIGN_MIGRATION.md`.

## 1. MD-файлы: белый список

Разрешено редактировать ровно следующие файлы; создавать новые MD вне белого списка запрещено:

- `README.md` — запуск, стек, демо-данные, траблшутинг
- `ARCHITECTURE.md` — слои, режимы, расчёты, контракты, снепшоты, тест-стратегия
- `plans/*.md` — история планов и статусов задач (каждая задача — отдельный файл, см. раздел 2)
- `backend/README.md` — документация бэкенда
- `DESIGN_MIGRATION.md` — дизайн
- `provisions/design-pack/**.md` — источник правды дизайна (brand/components/AGENTS)

Отчёты, `_REPORT.md`, `FINAL_*.md`, `*_SUMMARY.md` и прочие новые MD вне белого списка — запрещены.

## 2. Планы: папка `plans/`

Планы ведутся в папке `plans/` и копятся (история не удаляется, не перезаписывается).

### Имя файла
`plans/YYYY-MM-DD-<краткое-название-задачи>.md` (например, `plans/2026-10-28-catalog-snapshot-isolation.md`). Slug — латиница, lowercase, дефисы.

### Обязательные секции плана

```
# Plan: [Название задачи]

Status: IN_PROGRESS | DONE | CANCELLED
Created: YYYY-MM-DD
Closed: YYYY-MM-DD   # заполняется при закрытии

## Цель
Краткое описание того, что нужно сделать.

## Контекст
Ссылки на ARCHITECTURE.md, предыдущие планы, ограничения, требования пользователя.

## Подзадачи (максимум 10)
Для каждой:
- ID: 1..10
- Название
- Файлы: список файлов для создания/изменения
- Зависимости: ID подзадач, которые должны быть выполнены раньше
- Действия: конкретные шаги
- Критерии приёмки: как проверить готовность
- Статус: [ ] TODO / [~] IN_PROGRESS / [x] DONE

## CI
Ссылки на workflow run, известные baseline-красные (CI-1, CI-2, ...).

## Known bugs
Список известных дефектов, возникших в процессе работы.

## Backlog
Что осталось за скобками текущей задачи.

## Результаты
Заполняется при закрытии: краткая сводка изменений.
```

### Правила работы с планами
- Перед созданием нового плана — `ls plans/` и поиск активного (`Status: IN_PROGRESS`) на похожую тему. Если есть — продолжить его, а не создавать новый.
- Активный план в репозитории может быть только один.
- Закрытие плана = смена `Status: IN_PROGRESS` на `DONE` или `CANCELLED` + заполнение `Closed` и `Results`.
- Все ссылки в коммитах и отчётах («см. задачу в PLAN») теперь ведут на конкретный файл в `plans/`.

## 3. Workflow: Plan → Implement (для больших задач)

### Фаза 1: Планирование (текущая сессия)

При получении задачи, затрагивающей более 5 файлов или требующей архитектурных решений:

1. Проверь `plans/` на активные планы.
2. Создай новый план по шаблону выше.
3. Покажи план пользователю и дождись подтверждения.
4. НЕ начинай писать код в этой же сессии.

### Фаза 2: Реализация (новая сессия)

1. Пользователь начинает новую сессию (очистка контекста).
2. В новой сессии: «Прочитай `plans/<имя>.md` и выполни Подзадачу N. После завершения обнови статус подзадачи в плане.»
3. Каждая подзадача — отдельная сессия с чистым контекстом.
4. После всех подзадач — финальная проверка, смена статуса плана на `DONE`, заполнение `Results`.

### Когда этот workflow НЕ нужен
- Фикс-тикеты с 1–3 файлами правок.
- Доработка текущей подзадачи в уже активном плане (не начинай новую сессию, продолжай в контексте плана).
- Быстрые правки документации.

## 4. Работа с LLM и контекстным окном

- Никогда не загружай весь код проекта в контекст сразу — только релевантные файлы текущей подзадачи.
- План в `plans/` — внешний носитель памяти. Там хранятся решения, прогресс, known bugs; не держи их в голове между сессиями.
- Очищай контекст между фазой планирования и реализацией, между подзадачами, между несвязанными задачами.
- Требуй объяснений для сложных решений.
- Проверяй edge cases: null, пустые коллекции, ошибки сети, чужие `trip_id`.
- Требуй обработку ошибок с понятными сообщениями.
- Проверяй безопасность: SQL injection, XSS, CSRF, IDOR (чужой поход → 404).

## 5. Формат отчёта

```
Workflow run: <URL>
backend: passed/failed
frontend: passed/failed
docker: passed/failed
security: passed/warning/failed
test: passed/failed

<3-5 строк: что сделано, что проверено, что осталось>
```

Обязательно: ссылка на workflow run (без неё статус «не проверено»), статусы всех джобов, честное указание baseline-красных сьютов (см. активный план в `plans/`, секция «CI»). Запрещено: дублировать план, писать длинные простыни, приписывать гейты, которые не прогонял.

## 6. Запрет на генерацию SHA

SHA для actions указывать только из GitHub UI (Releases/коммит) или официальных документов; рукописные/придуманные SHA запрещены. Предпочтительны версии по тегам (`@v4`).

## 7. Запрет на смену архитектуры в фикс-тикетах

Фикс-тикет меняет поведение только в рамках заявленного дефекта. Новые сущности/эндпоинты/слои — через отдельную задачу с планом в `plans/`. Исключение: защитные проверки (ownership, валидации) в том же тикете.

## 8. Баг-тесты и @Disabled

- На каждый баг — сначала падающий тест (red), затем фикс (green). Ссылка на тест в коммите.
- `@Disabled`/`it.skip` допустимы только с TODO-комментарием и ссылкой на задачу в `plans/`; страж R4 грепает глушилки без следа.
- Baseline-красные сьюты (например, `EconomicConsistencyTest` до CI-1) не «чинятся» попутно в неродных тикетах и не маскируются: указываются в отчёте как baseline.

## 9. Проверка перед коммитом (ритуал)

```
# Backend (PowerShell 5.1: использовать ; вместо &&)
# ВАЖНО: всегда использовать -o (offline), чтобы Maven не проверял обновления
# и не зависал на сетевых операциях при старте тестов
cd backend; JWT_SECRET=<32+ символов> mvn -B -o test
# Frontend
npx tsc --noEmit          # typecheck (гейт CI с T0)
npm run lint
npm run test
npm run test:coverage     # R5: lines ≥80% per-file на зоне изменения
# MD-файлы
git ls-files '*.md'       # сверить с белым списком раздела 1
# Планы
ls plans/                 # свериться с активным планом: все ли подзадачи закрыты
```

Затронуты эндпоинты с mock-паритетом → `CONTRACT_TARGET=mock npm run test:contract` и сверка форм ответов с бэком (раздел 14, триггеры). E2E-зона → `npm run test:e2e` (mock) и, для real-сценариев, против поднятого compose-стека.

## 10. Работа с CI

- Не мержить при красном CI по собственной вине; кросс-веточные конфликты ловятся обновлением ветки перед merge (up-to-date before merge).
- Non-blocking джобы (security scans, contract nightly, e2e на PR) не оправдывают игнор их падений: падения разбираются и закрываются задачами в `plans/`.
- Новые workflow-шаги с внешними зависимостями (apt, docker hub) писать с фолбэками и комментариями-причинами (урок: PGDG-fallback, `-U` для Maven Central 502).

## 11. Миграции и схема

- Только новые номера (следующий — V21). Применённые миграции НЕ править и НЕ удалять (урок V14/V15: удаление ломает существующие БД и чужие деплои).
- Бэкфил данных допустим внутри новой миграции; повторный прогон обязан быть безопасен (IF NOT EXISTS / ON CONFLICT / DROP temp-таблиц в начале — урок V20 и TestDataIsolation, перенакатывающей Flyway в той же сессии).
- `ddl-auto=validate`: любая колонка в JPA-сущности обязана существовать в миграции до старта приложения.
- Сид-данные каталога — только миграциями (V3/V17/V18-паттерн): код, имя, единица, kcal/100 г, piece_weight_g для PCS/PACK, pack_size+round_to_packs, цена RUB на 2026-01-01 + 24 мес. истории.

## 12. Снепшоты каталога (V20): обязательные следствия для нового кода

- Каталожные выборки (UI-справочники, админ, дубль-чеки) фильтруют `trip_id IS NULL`; расчётные выборки по id ингредиентов похода — НЕ фильтруют (копии).
- Страницы похода читают блюда/цены только через `GET /trips/{id}/recipes` и `GET /trips/{id}/prices`; глобальные `/recipes`, `/prices` — для каталога и админа.
- Новые ссылки «поход → продукт/блюдо» (фичи, правки) обязаны указывать на trip-scoped копию (создавать через `TripCatalogSnapshotService`), иначе возвращаем блокировки справочника.
- Уникальность имён продуктов — только среди глобальных (partial-индекс); копии создаются с `code = NULL`.
- Mock-паритет: новые эндпоинты и семантики (latest-срез цен, снепшоты при добавлении приёма, дни при создании похода, composition batch PUT) реализуются в `mockServer.ts` в том же тикете + contract-тест. Mock-сводки `/summary/*` обязаны считать из meals/edits/exclusions, а не отдавать фикстуры (долг R8, см. активный план).
- Данные похода — только сервер: новые localStorage/`tripStaging`-хранилища для правок, исключений и факта запрещены; существующие — долг R1/R2, не расширять.
- Деньги и ккал на клиенте не пересчитываются: страницы похода читают `/summary/*`, клиент только форматирует (`formatRub`, `humanize`). Исключение — preview в админ-редакторах и live-итоги модалок до сохранения.

## 13. Правила кодинга фич (R1–R9)

- R1. Тест до кода (red-green) для любого бага и новой математики/логики.
- R2. Слой теста = слой изменения (unit/service/integration/component/e2e — без «страховочных» дублей).
- R3. Фича не готова без своего теста и без mock-паритета, если затронуты эндпоинты.
- R4. Запрет глушить тесты без следа (@Disabled + TODO + задача в `plans/`).
- R5. Coverage на новом коде: lines ≥80% per-file; новый компонент добавляется в `coverage.include` vitest.config.
- R6. Кодер НЕ утверждает: «CI зелёный» без ссылки на run; «контракт не сломан» без прогона contract; «миграция безопасна» без прогона на существующей БД.
- R7. Отчёт — формат раздела 5, без новых MD.
- R8. Размер файла: 300–500 строк максимум. Если файл становится больше — выполняй декомпозицию по ответственности, а не механически по строкам. Одна связная ответственность на модуль; не смешивай бизнес-логику, инфраструктуру и утилиты.
- R9. Одна ответственность на модуль. Разделяй файлы по функциональному назначению, а не только по количеству строк. Не жертвуй логической связностью или читаемостью кода ради соблюдения произвольных ограничений.

## 14. Полнота изменения: системный подход

### Матрица сопряжённых слоёв

| Меняю | Проверить |
|---|---|
| DTO/контракт ответа | mockServer-форму, contract-тесты, типы фронта (`number` для id/денег в новом коде), e2e-ассерты |
| Расчёт в SummaryService | by-days/shopping/person/kpi согласованность (инвариант сумм), mock-расчёт, contract-фикстуры |
| Схема/миграция | JPA-сущность (validate), existing-DB прогон, TestDataIsolation-перенакат, сид-тесты CatalogIntegration |
| Эндпоинт похода | ownership/IDOR-тест (чужой поход → 404), swagger, mock-роут, права ролей |
| Продукт/рецепт (справочник) | каталожные фильтры `trip_id IS NULL`, usedIn-проверки, снепшот-копии не затронуты |

### Триггеры «если → то»

- Новый эндпоинт → + mock-роут + contract-тест + ownership-тест + swagger-проверка.
- Новая математика денег/ккал → эталон округлений ARCHITECTURE + unit-фикстуры + contract.
- Новый компонент фронта → тесты + coverage include + дизайн-токены (не хардкод-цвета).
- Правка сида каталога → обновление чисел в README/ARCHITECTURE и ожиданий CatalogIntegrationTest (счётчики сверять с БД-запросом, не хардкодить).
- Правка математики состава (EXTRA/substitution/SCALE) → `mealCompositionContract.test.ts` зелёный на mock и бэк-фикстурах + инвариант сумм by-days/shopping/person + актуализация девиаций в ARCHITECTURE.

## 15. Тест-гигиена (уроки аудита)

- Интеграционные тесты — только `@ContainerSuite`/`LocalPgFallback` (или Testcontainers); голый `localhost:5432` в тестах запрещён (урок EconomicConsistencyTest).
- Тесты не зависят от коллации/порядка имён: выбор целей структурный (первый подходящий по форме), а не по точному имени сида; счётчики каталога сверять с независимым SQL-запросом.
- Payload-ы тестов соответствуют актуальным DTO (обязательные поля: `categoryId` у продукта, `pieceWeightG` для PCS/PACK с kcal).
- Кириллица в тестах: файлы в UTF-8, сравнения строк — через данные ответа, не через литералы, где можно.

## 16. Checklist перед коммитом

- [ ] Ритуал раздела 9 зелёный (с указанием baseline-красных)
- [ ] Активный план в `plans/` актуален: подзадачи закрыты, Known bugs заполнен
- [ ] Новый код покрыт (R5), глушилок без TODO нет (R4), файлы ≤500 строк (R8), по одной ответственности (R9)
- [ ] Mock-паритет и contract для затронутых эндпоинтов; mock-сводки считают, а не фикстурят
- [ ] Нет новых localStorage-хранилищ данных похода; клиент не пересчитывает деньги/ккал
- [ ] Миграции: новый номер, повторный прогон безопасен, existing-DB проверена
- [ ] MD: правки только в белом списке; числа/статусы синхронизированы (README/ARCHITECTURE/активный план)
- [ ] Отчёт по форме раздела 5 приложен к PR
- [ ] Для задач >5 файлов: создана отдельная сессия реализации после планирования (раздел 3)

## 17. Примеры

### Правильный отчёт

```
Commit: 8b88fc55
Workflow run: https://github.com/.../runs/...
backend: passed (baseline: EconomicConsistencyTest red, план plans/2026-10-20-ci-1.md CI-1)
frontend: passed
docker: failed (baseline CI-2, логи запрошены)
security: warning (trivy non-blocking, 0 CRITICAL unfixed)
test: passed

V20 снепшоты: миграция с бэкфилом, snapshot-сервис, trip-scoped /recipes и /prices.
Проверено: SnapshotIsolationIntegrationTest 3/3, mock-паритет, existing-DB прогон.
Осталось: T6 (фронт на /summary), CI-2 логи раннера.
```

### Неправильный отчёт

«Всё готово, тесты зелёные, можно мерджить» (без ссылок, без baseline, без списка проверок, без ссылки на план).

## 18. Главное правило

Ты — помощник разработчика, а не автономный агент.

Все решения должны быть:
1. Прозрачными — объясняй, почему делаешь именно так.
2. Проверяемыми — предоставляй способы проверить результат.
3. Обратимыми — не делай деструктивных действий без подтверждения.
4. Контролируемыми — пользователь всегда имеет последнее слово.

Никогда не коммить изменения без прямой просьбы пользователя.
