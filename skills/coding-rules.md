# Skill: правила качества кода (R1–R12)

- **R1.** Тест до кода (red→green) для любого бага и новой математики/логики.
- **R2.** Слой теста = слой изменения (unit/service/integration/component/e2e), без «страховочных» дублей.
- **R3.** Фича не готова без своего теста; затронуты эндпоинты → mock-паритет + contract-тест.
- **R4.** Запрет глушить тесты без следа: `@Disabled`/`it.skip` только с TODO + ссылка на файл в `tasks/`.
- **R5.** Coverage нового кода: lines ≥ 80% per-file; новый компонент → в `coverage.include` vitest.config.
- **R6.** Не утверждать без прогона: «CI зелёный» без run, «контракт цел» без contract-теста,
  «миграция безопасна» без прогона на существующей БД.
- **R7.** Отчёт — формат `skills/close-task.md`, новых MD-отчётов не создавать.
- **R8.** Файл ≤ 500 строк (цель 300). Больше — декомпозиция по ответственности.
- **R9.** Одна ответственность на модуль; не смешивать бизнес-логику, инфраструктуру, утилиты.
- **R10.** Логирование: по логу видно кто/кого/с чем вызвал и какую ошибку получил.
- **R11.** Документация обновляется вместе с кодом — карта в `skills/docs-sync.md`.
- **R12.** Миграции — только `skills/migrations.md` (новый номер, rerun-safe, validate).

## Матрица сопряжённых слоёв (что проверить вместе с правкой)
| Меняю | Проверить |
|---|---|
| DTO/контракт ответа | mockServer-форму, contract-тесты, типы фронта, e2e-ассерты |
| Расчёт в SummaryService | by-days/shopping/person/kpi (инвариант сумм), mock-расчёт, contract-фикстуры |
| Схема/миграция | JPA-сущность (validate), existing-DB прогон (`FlywayUpgradeIntegrationTest`), сид-тесты |
| Эндпоинт похода | ownership/IDOR-тест (чужой поход → 404), swagger, mock-роут, права ролей |
| Продукт/рецепт (справочник) | каталожные фильтры `trip_id IS NULL`, usedIn-проверки, снепшот-копии не затронуты |

## Триггеры «если → то»
- Новый эндпоинт → mock-роут + contract-тест + ownership-тест + swagger.
- Новая математика денег/ккал → эталон округлений в ARCHITECTURE + unit-фикстуры + contract.
- Новый компонент фронта → тесты + coverage include + дизайн-токены (НЕ хардкод-цвета,
  не сырая палитра Tailwind; образец — `.toast*`/`.alert--*` в `src/index.css`).
- Правка сида каталога → числа в доках + ожидания `CatalogIntegrationTest` (сверять SQL-запросом).
- Правка математики состава → `mealCompositionContract.test.ts` (mock+бэк) + инвариант сумм.

## Тест-гигиена
- Интеграционные тесты — только `@ContainerSuite`/LocalPgFallback; голый `localhost:5432` запрещён.
- Тесты не зависят от порядка/имён сида: выбор структурный; счётчики каталога сверять SQL-запросом.
- Payload-ы соответствуют актуальным DTO (`categoryId` у продукта, `pieceWeightG` для PCS/PACK).
- Файлы в UTF-8; кириллица в сравнениях — через данные ответа, где можно.

## Безопасность (минимум)
SQL injection, XSS, CSRF, IDOR (чужой `trip_id` → 404), rate-limit на auth-эндпоинтах,
секреты только из ENV (fail-fast при коротком JWT_SECRET).

## Контраст в светлой теме (WCAG AA ≥4.5:1)
- **amber-300 (#D97418) НЕ проходит AA на белом фоне** для мелкого текста — 3.25:1.
  Никогда не используй `--amber-300` как цвет текста для `<18px` элементов в light-теме.
- `color-mix(amber-500 N%, transparent)` на `bg-1` (#FFFFFF) ещё ухудшает: чем меньше alpha,
  тем ближе фон к белому, тем ниже контраст. Даже `amber-600` при alpha=14% даёт лишь 3.84:1.
- **Фикс-паттерн:** в hover/active состояниях светлой темы для иконок-кнопок используй
  `--amber-600` + `background: transparent` (solid) вместо `color-mix`.
  amber-600 на чистом bg-1 = 4.50:1 ✅, dark-тема = 6.17:1 ✅.
- Всегда проверяй контраст компонентов с прозрачным фоном в light-теме — тёмная тема
  (`bg-1=#101D27`) «прощает» `color-mix` с низкой alpha, белая — нет.
