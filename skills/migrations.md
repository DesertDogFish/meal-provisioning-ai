# Skill: миграции БД (Flyway)

## Железные правила
1. **Только новый номер**: следующий = максимум в каталоге + 1.
   ```bash
   ls backend/src/main/resources/db/migration/ | grep -oE '^V[0-9]+' | sort -V | tail -1
   ```
   Номер НЕ фиксировать в доках прозой (устаревает) — источник правды только каталог.
2. **Применённые/опубликованные миграции НЕ править и НЕ удалять** (checksum; урок V14/V15
   и дубля V30). Ошибка в старой миграции → новая миграция-исправление.
3. **Повторный прогон безопасен**: `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` / `DO $$ ... END$$`
   проверки; temp-таблицы дропать в начале.
4. `ddl-auto=validate`: каждая колонка JPA-сущности обязана существовать в миграциях ДО старта.
   Добавил поле в сущность — добавь колонку в той же задаче.
5. Дубли номеров ловит CI (job Repo Hygiene, шаг «No duplicate Flyway migration versions»).

## После правки миграций (песочница)
1. Вычистить stale-копии: `rm backend/target/classes/db/migration/<старые-имена>.sql`
   (mvn не удаляет пропавшие из исходников ресурсы — иначе «more than one migration»).
2. Дропнуть ВСЕ тестовые БД `provision%` (команда в `skills/testing.md`).
3. Прогнать: `SnapshotIsolationIntegrationTest` (старт схемы) и `FlywayUpgradeIntegrationTest`
   (апгрейд существующей БД) — команды в `skills/testing.md`.

## Документация (в той же сессии, R11)
- `backend/README.md` §Миграции: пункт о новой миграции (1–3 строки: что и зачем).
- `ARCHITECTURE.md` §Database: если менялась структура/смысл данных.
- Диапазоны версий прозой НЕ писать («V1–V35» устаревает) — ссылка на каталог.
