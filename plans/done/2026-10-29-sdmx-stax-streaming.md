## Цель

Убрать ограничение на объём выгрузки ЕМИСС: читать SDMX-ответ **потоково** (StAX), а не строить
DOM целиком, чтобы полный ряд (все товары × 27 лет, 65 076 787 байт) разбирался в пределах
типового heap, а окно выгрузки можно было расширять без страха OOM.

Закрывает `KB-1` и снимает гап `KB-2` (ось «Год» в запросе к порталу остаётся полной — сужать
её и не нужно, если объём ответа перестаёт быть ограничением). Заодно закрывает `BL-17`.

## Контекст

- Реестры: `plans/knownbugs.md` (KB-1, KB-2, KB-10), `plans/backlog.md` (BL-15, BL-17, BL-18, BL-20).
- Протокол и решение «портал — только транспорт, всё читается из локальной копии» —
  `ARCHITECTURE.md` и закрытый план `plans/done/2026-10-28-emis-download-csrf-and-volume.md`.
- Текущая реализация: `RosstatEmisProvider.parseSdmx(String xml, String regionTitle)` —
  `DocumentBuilderFactory` + DOM целиком. Вызовы: ответ портала (`data.body()`, строка ~362)
  и проверка файла, загруженного админом (строка ~265). Предохранитель
  `integration.rosstat.max-response-bytes: 33 554 432` **отказывает в разборе**, если ответ
  больше, — то есть полный ряд сегодня не разбирается вообще.
- Форма ответа (боевой fedstat.ru, SDMX 1.0 GenericData): `CodeLists` (885 товаров, 450 ОКАТО)
  всегда полные и идут **до** `DataSet`; в рядах месяц — атрибут ряда
  `Attributes/Value[@concept="PERIOD"]` (русское название), год — в `Obs/generic:Time`.
  Годовые ряды без месяца дают 1 января (дефект №7 закрытого плана).
- Сетка безопасности: `RosstatEmisProviderTest` — 26 тестов, включая разбор боевой фикстуры
  `backend/src/test/resources/emis/data-31448-real.xml`. Фикстуры не правим: результат разбора
  обязан остаться прежним.
- Ограничения среды (`KB-10`): тяжёлые сьюты в песочнице агента не запускаются (OOM), живой
  портал из зарубежного ЦОД недоступен (403 анти-бот), Docker-демона нет. Транспорт поэтому
  проверяется на фикстурах и владельцем вручную; `gh`/CI из песочницы недоступны.
- `AGENTS.md` §7: архитектурные изменения внутри фикса запрещены — hence отдельный план.
- `AGENTS.md` §12: данные похода только с сервера; к задаче не относится, но разбор выгрузки
  остаётся серверным (никакого парсинга XML на клиенте).

### 2. Транспорт: тело ответа потоком, а не строкой

- Файлы: `RosstatEmisProvider.java` (`JdkTransport`, `downloadData.do`),
  `backend/src/main/resources/application.yml` (комментарий к `max-response-bytes`).
- Зависимости: 1.
- Действия:
  - `BodyHandlers.ofInputStream()` вместо `ofString()` — ответ не материализуется в `String`
    (65 МБ XML = ~130 МБ `String` + DOM ~600–700 МБ heap — ровно то, что убирал предохранитель).
  - Первые ~4 КБ читать через `PushbackInputStream` и использовать для диагностики: HTML вместо
    SDMX, страница логина, 302, 503. Тексты ошибок в журнале синков сохраняются (дефект №5
    закрытого плана не регрессирует).
  - `max-response-bytes` меняет смысл: не «отказаться парсить большой ответ», а **оборвать чтение**
    на превышении с внятной причиной («ответ больше N МБ — увеличьте лимит или сузьте окно»).
- Критерии приёмки: существующие тесты на ошибочные ответы зелёные; при чтении фикстуры 65 МБ
  пик heap не растёт пропорционально объёму (прогон с `-Xmx128m` на сгенерированном большом
  SDMX не падает и даёт те же счётчики, что `-Xmx512m`).
- Статус: [x] DONE 29.10.2026 — в `Session` добавлены `record StreamResult(int status,
  InputStream body, String contentType, String location)` и `default postFormStream(...)`
  (обёртка над `postForm` → `ByteArrayInputStream`), поэтому `FakeTransport` в тестах не менялся;
  `JdkTransport` переопределяет его через `BodyHandlers.ofInputStream()`. `downloadAndParse`
  читает первые ≤4 КБ через `PushbackInputStream` (`HEAD_BYTES`) и отдаёт их в `describeHead` —
  диагностика 302/не-200/`text/html`/CSRF сохранена дословно (тесты ассертят эти фрагменты).
  **Проверено памятью**: скретч-харнес `/tmp/harness3/BigSdmx.java` сгенерировал 66,2 МБ SDMX
  (885 товаров × 27 лет × 2 региона) — разбор при `-Xmx128m` за ~4,3 с, 286 740 точек,
  регион 643004.АГ отфильтрован; лимит 1 МБ обрывает чтение с `IntegrationUnavailableException`.

### 3. Загрузка файла админом — тоже потоком

- Файлы: `RosstatEmisProvider.java` (`parseSnapshot`/проверка файла),
  `backend/src/main/java/com/provision/service/IntegrationService.java` (`uploadSnapshot`).
- Зависимости: 1.
- Действия: `MultipartFile.getInputStream()` вместо `getBytes()` → `new String(...)`;
  ограничение размера — как в подзадаче 2 (считать байты по ходу чтения).
- Критерии приёмки: файл 65 МБ загружается через «Интеграции → Загрузить файл выгрузки» при
  `-Xmx256m`; счётчики `products/prices/deleted` в журнале совпадают с прежними;
  пустой файл по-прежнему даёт `EMPTY_FILE`, неизвестный провайдер — 404.
- Статус: [x] DONE 29.10.2026 (с отступлением от плана) — `new String(payload)` убран: признак
  SDMX ищется в первых 64 КБ (`SNIFF_BYTES`), разбор идёт через `ByteArrayInputStream(payload)`
  в тот же потоковый `parseSdmx`. **Отступление**: `MultipartFile.getInputStream()` не применён,
  потому что байты пересекают границу `@Async` (`self().executeUploadSync(...)` в
  `IntegrationService`): во фоновом потоке временный файл multipart уже может быть удалён,
  поэтому интерфейс `parseSnapshot(byte[], fileName)` сохранён намеренно. Главное достигнуто —
  разбор больше не удваивает объём (`String` на ~130 МБ не создаётся). Критерий «файл 65 МБ
  при -Xmx256m» в песочнице **не проверен** (нет Docker, тяжёлые прогоны не запускаются, KB-10);
  память разбора доказана харнесом на 66,2 МБ при `-Xmx128m`.

## Результаты

**Сделано.** SDMX-ответ портала разбирается потоково: `SdmxStreamParser.parse(InputStream,
regionTitle, maxBytes)` — один проход по событиям с захватом поддерева `CodeList`/`Series`,
в heap живёт один ряд; DTD и внешние сущности запрещены; ряды раньше словарей буферизуются
(потолок 10 000); `LimitedInputStream` обрывает чтение на `max-response-bytes`. Транспорт отдаёт
тело потоком (`EmisTransport.StreamResult` + дефолтный `postFormStream`, совместимый с тестовыми
фейками), диагностика отказа собирается по голове ответа ≤ 4 КБ. Ручная загрузка файла админом
идёт тем же парсером. Лимиты объёма согласованы в 96 МБ в семи местах (`application.yml`,
`docker-compose.yml`, `.env.example`, `nginx.conf`, `IntegrationsPage.tsx` и комментарии),
память контейнера задана явно: `mem_limit: ${BACKEND_MEM_LIMIT:-1g}` + `MaxRAMPercentage=70.0`
(BL-18). Провайдер декомпозирован (BL-15): 1091 → 355 строк, семь модулей, все ≤ 500.

**Проверено (чем).** `RosstatEmisProviderTest` 34/34 — **без правок фикстур** (критерий приёмки
владельца: было 26, добавлено 9 на ветки диагностики и стриминга); `SdmxStreamParserTest` 16/16;
`RosstatConfigBindingTest` 3/3; `EmisUnitTest` 20/20; `EmisCatalogServiceTest` 16/16;
`EmisControllerTest` 5/5 (итого 94/94 одним прогоном по классам); `EmisSharedCountIntegrationTest`
5/5 на реальной PostgreSQL (своя БД `provision_test_emis_shared`, `LocalPgFallback`). Покрытие
jacoco 0.8.12: `SdmxStreamParser` 91,4 % инструкций / 73,6 % ветвей (критерий ≥ 80 % выполнен),
пакет `integration` 84,7 % / 70,9 %. Память на полном объёме: 66,2 МБ (286 740 точек, 885 позиций)
разобраны за 4,3 с при `-Xmx128m` — DOM на том же файле требовал 600–700 МБ. Фронтенд:
`npx tsc --noEmit` чистый, eslint чистый, полный сьют vitest **482/482** (54 файла), включая новые
`src/api/contractEmis.test.ts` (21) и значок со счётчиком в `ProductTable.test.tsx` (25 в файле);
`npm run test:contract` 56/56.

**Не проверено (честно).** CI: workflow run нет — из песочницы `gh`/GitHub Actions недоступны,
статусы джобов **не проверены**. Тяжёлые сьюты `UserPricesIntegrationTest`,
`EconomicConsistencyTest`, `DockerStackSmokeTest` не прогнаны из-за лимита памяти песочницы
(KB-10, OOM-kill 137 даже на чистом HEAD); `docker compose config`/`up` не выполнялись —
Docker-демона в песочнице нет, поэтому `mem_limit`/`MaxRAMPercentage` проверены только чтением
конфигов. Живой портал из зарубежного ЦОД недоступен (403 анти-бот): `JdkEmisTransport` остаётся
с нулевым покрытием, боевой прогон полного ряда (927 `selectedFilterIds`, 65 076 787 байт) —
на стороне владельца. Полный бэкенд-сьют (`mvn test`) не гонялся — только перечисленные классы.

**Риски.** (1) Поток портала в песочнице не воспроизводится: если живой ответ отличается от
фикстуры (порядок `CodeLists`/`DataSet`, новые атрибуты ряда), это поймает только прогон
владельца — страховка: буферизация рядов до словарей и внятные ошибки разбора. (2) Доказательство
памяти получено харнесом вне дерева и в CI не повторяется → BL-24. (3) `max-response-bytes: 96MB`
и `MaxRAMPercentage=70.0` согласованы расчётом, а не замером в контейнере. (4) Golden-фикстур
страницы с токеном нет (BL-20): изменение вёрстки портала диагностируется текстом ошибки, а не тестом.
